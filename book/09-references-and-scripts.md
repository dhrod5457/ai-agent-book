# 9장. References와 Scripts

Skill이 커질 때 가장 흔한 반응은 SKILL.md에 섹션을 계속 추가하는 것이다.

하지만 세부 정보와 반복 작업을 모두 본문에 두면 Skill은 다시 상시 매뉴얼처럼 변한다.

References와 Scripts는 단순한 파일 분리가 아니라 문맥 정보와 책임을 분리하는 도구다.

## 9.1 Root Skill은 router에 가깝게

Skill 본문에는 시작 조건, 핵심 작업 절차(workflow), 필요한 분기, 완료 조건이 있어야 한다.

긴 API 규약, 모든 예외 사례, 상세 예제, 전체 CLI 옵션 표까지 넣을 필요는 없다.

필요한 세부 자료는 참고 자료로 분리한다. 이때 본문에 “자세한 내용은 references를 보라”고만 쓰지 말고, 언제 어떤 자료를 읽어야 하는지 조건을 적는다.

## 9.2 Reference에 적합한 내용

다음은 참고 자료 후보가 된다.

- 긴 API 규약
- 복잡한 데이터 구조 규칙(schema)
- 예외 사례 목록
- 호환성 정책
- 순차 적용 정책
- 상세 예제
- 장문의 스타일 가이드
- 특정 버전 이전 안내 문서

이 정보는 매번 필요하지 않다.

## 9.3 Reference depth를 얕게 유지한다

SKILL.md가 참고 자료 A를 가리키고, A가 B를 가리키고, B가 다시 C를 가리키면 모델은 필요한 정보를 찾기 위해 깊은 탐색을 해야 한다.

좋은 구조는 진입점에서 필요한 자료를 직접 찾기 쉽다.

긴 참고 자료 자체에는 목차를 둘 수 있지만, 참고 자료 체인을 계속 늘리지는 않는다.

## 9.4 Cached CLI Manual

빠르게 변하는 CLI의 옵션과 플래그를 SKILL.md에 복제하면 시간이 지나면서 두 개의 기준 정보가 생긴다.

실제 CLI와 Skill의 설명이 어긋나기 시작한다.

이때 더 좋은 자료는 상황에 따라 다음이 될 수 있다.

- 설치된 CLI의 help
- 자동 생성된 데이터 구조 규칙
- 설치된 버전의 문서
- 현재 확인할 수 있는 공식 문서

Skill은 옵션 전체를 복제하는 대신 **어떤 자료를 언제 읽을지** 알려준다.

## 9.5 Latest가 항상 정답은 아니다

빠르게 변하는 프레임워크나 API를 다룰 때 현재 공식 문서만 보면 충분하지 않을 수 있다.

기존 프로젝트는 특정 실행 환경, 호환성 날짜, SDK, 타입 버전에 의도적으로 고정되어 있을 수 있다.

따라서 자료의 우선순위를 둔다.

1. 사용자가 지정한 대상
2. 프로젝트 설정의 대상
3. 설치된 패키지와 자동 생성된 데이터 구조 규칙
4. 현재 공식 자료
5. 대체 자료로 보존해 둔, 날짜가 표시된 사본

업그레이드 작업과 기존 코드 리뷰는 같은 기준을 사용하지 않는다.

## 9.6 Script가 prose보다 나은 경우

같은 기계적 절차를 매번 자연어로 설명한다면 스크립트 후보다.

예:

- 링크 검사 도구
- Skill 참고 자료 검사 도구
- 코드 서식 정리 도구
- 반복 변환
- 산출물(artifact) 비교
- 데이터 구조 규칙 검사
- 전송할 데이터 생성

스크립트는 지식을 숨기는 장치가 아니다. 결정론적으로 실행 가능한 부분을 자연어 추론에서 분리하는 장치다.

## 9.7 Script contract

Skill에서 스크립트를 호출하려면 다음이 분명해야 한다.

- 언제 실행하는가.
- 입력은 무엇인가.
- 성공과 실패 종료 코드가 무엇인가.
- 출력이 무엇을 의미하는가.
- 파일이나 외부 시스템을 변경하는가.
- 재실행해도 안전한가.
- 시간 제한이나 실행 후 정리가 필요한가.

스크립트가 있다고 해서 자동으로 신뢰할 수 있는 것은 아니다.

## 9.8 Executable state machine

복잡한 작업 절차는 자연어로 10단계를 길게 설명하기보다, 상태를 기계가 읽을 수 있는 형식으로 기록하고 스크립트가 상태 변경을 검증하게 하는 편이 나을 수 있다.

예를 들어 prepare → validated → approved → deployed 같은 작업 절차에서 어떤 상태를 누가 만들 수 있는지 코드로 검사할 수 있다면 자연어 중복이 줄어든다.

다만 모든 작업 절차를 상태 기계로 만들 필요는 없다. 기계적 판정이 명확하고 상태 충돌이 실제 문제일 때 사용한다.

## 9.9 Canonical source를 복제하지 않는다

디자인 토큰, DB 데이터 구조 규칙, 자동 생성된 타입, CI 기준값, API 규약이 이미 기계가 읽을 수 있는 자료에 있다면 Skill에 값을 다시 적지 않는다.

Skill은 다음을 말하면 된다.

> 이 작업에서는 해당 기준 원본(canonical source)을 먼저 읽고, 그 값을 사용한다.

복제하지 않는 것이 최신성을 유지하는 가장 강한 방법이다.

## 9.10 본문과 resource의 경계

SKILL.md에는 Skill을 선택한 뒤 즉시 필요한 판단을 남긴다. references에는 조건에 따라 읽을 상세 지식을, scripts에는 같은 조건에서 같은 결과를 내는 절차를, assets에는 산출물을 만들 재료를 둔다.

이 경계가 선명할수록 Skill은 커져도 필요한 순간에 필요한 정보만 읽는 구조를 유지할 수 있다.

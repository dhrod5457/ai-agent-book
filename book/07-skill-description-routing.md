# 7장. description이 Skill의 절반이다

Skill 작성에서 가장 과소평가되는 부분은 본문이 아니라 설명 필드인 description이다. 이 필드는 단순한 소개 문장을 넘어, 모델이 수많은 후보 중 요청에 맞는 Skill을 고르는 기준이 된다. 이를 **라우팅 인터페이스**라고 한다.

## 7.1 무엇을 하는가와 언제 쓰는가

좋은 description은 두 질문에 답한다.

- 이 Skill은 무엇을 하는가.
- 어떤 요청에서 사용해야 하는가.

둘 중 하나만 있으면 부족하다.

“DB 작업을 돕는다”는 무엇을 하는지조차 넓고, 언제 쓰는지 알 수 없다.

“데이터베이스를 변경하거나 이전하는 마이그레이션(migration)을 추가하거나 수정하거나 순차 적용을 검토할 때 사용한다”는 실제 작업 유형을 호출 조건(trigger)으로 제공한다.

## 7.2 도메인을 trigger로 쓰지 않는다

Skill을 과잉 호출시키는 가장 흔한 패턴은 도메인 전체를 호출 조건으로 잡는 것이다.

예:

> 데이터베이스 관련 작업에 사용한다.

이 문장은 질의 작성, 데이터 구조 규칙(schema) 탐색, 마이그레이션, 성능 조사, 단순 질문까지 모두 끌어들일 수 있다.

더 좋은 description은 **사건**을 쓴다.

- 새로운 마이그레이션을 만든다.
- 기존 마이그레이션의 순차 적용 안전성을 검토한다.
- 마이그레이션 실패를 복구한다.

Skill은 주제 분류기가 아니라 업무 라우터다.

## 7.3 Adjacent negative

호출해야 하는 조건만 적으면 인접 Skill과 충돌할 수 있다.

기능 추가(feature), 버그 수정(bugfix), 구조 개선(refactor), 검토(review)를 예로 들어보자.

“코드를 변경할 때 사용한다”는 네 Skill 모두에 적용될 수 있다.

경계를 더 명확하게 하려면 가까운 반례를 생각해야 한다.

- 이미 있어야 할 동작이 깨졌다면 버그 수정(bugfix)
- 동작 변화 없이 구조만 바꾸면 구조 개선(refactor)
- 구현 없이 검토만 하면 검토(review)
- 새로운 사용자 동작을 추가하면 기능 추가(feature)

이렇게 인접 책임을 구분하면 핵심 단어가 아니라 의도로 라우팅할 수 있다.

## 7.4 Negative boundary는 금지문 목록이 아니다

호출하지 않아야 하는 경계를 작성한다고 “이때 쓰지 마라”를 수십 개 나열할 필요는 없다.

가장 혼동하기 쉬운 경계만 적는다.

호출 제외 경계를 잘 정하면 분야 전체를 막지 않는다. 인접한 잘못된 선택을 줄인다.

예:

> 기존 마이그레이션의 동작을 분석만 하는 요청에는 사용하지 않는다. 실제 마이그레이션 변경이나 순차 적용 검토에서 사용한다.

## 7.5 Keyword stuffing

description에 가능한 모든 동의어와 키워드를 넣으면 필요한 대상을 빠짐없이 고르는 비율(recall)이 좋아질 것 같지만 항상 그렇지 않다.

문제가 되는 이유는 세 가지다.

첫째, 다른 Skill과 메타데이터(metadata)가 비슷해진다.

둘째, Skill 선택(routing)에 필요 없는 실행 세부사항이 항상 노출된다.

셋째, 넓은 단어가 필요 없는 Skill을 호출하는 오탐(false positive)을 만든다.

description은 검색 엔진용 SEO 문구가 아니다.

## 7.6 Skill inventory 전체를 함께 본다

새 Skill의 description만 보고 품질을 판단하면 안 된다.

설치된 Skill들은 서로 경쟁한다.

따라서 리뷰할 때 다음을 묻는다.

- 이 요청은 A와 B 중 어디로 가야 하는가.
- description만 보고 그 차이를 알 수 있는가.
- 둘 다 호출되어야 하는 경우가 있는가.
- 둘 다 호출되면 안 되는 요청은 무엇인가.
- 아무 Skill도 선택하지 않는 선택 없음 상태가 가능한가.

Skill 수가 늘어날수록 개별 문장보다 전체 목록에서 각 Skill의 역할이 얼마나 분명히 나뉘는지가 중요하다.

## 7.7 Manual-only Skill

배포, 비용 발생, 데이터를 삭제하거나 손상할 수 있는 작업처럼 명시적 호출이 필요한 Skill은 자동 Skill 선택 경쟁에서 빼는 것이 더 안전할 수 있다.

명시적으로 호출할 때만 실행하는 Skill은 자연어 호출 조건 정확도를 높이는 대신, 사용자가 명시적으로 시작한다는 계약을 가진다.

이 경우 중요한 것은 자동 호출 평가에서 제외하고, 명시적 호출과 입력 인자의 규약을 검증하는 것이다.

## 7.8 Description budget

짧다고 무조건 좋은 것은 아니다.

중요한 분기를 지나치게 줄이면 필요한 Skill이 호출되지 않는다. 실제 공개 Skill 유지보수에서도 라우터와 description을 줄인 뒤 새로 도입하는 요청을 알아보는 중요한 호출 조건이 사라져 다시 복구한 사례가 있다.

따라서 목표는 최소 길이가 아니다.

> 필요한 경계를 보존하면서 불필요한 설명을 제거하는 것.

## 7.9 Trigger-Driven Development

Skill을 먼저 쓰고 나중에 호출 조건을 생각하지 않는다.

description 초안을 만들기 전에 최소한 다음 요청을 준비한다.

- 이름이나 의도를 명시해 호출해야 하는 요청
- Skill 이름 없이 자연스럽게 말해도 호출해야 하는 요청
- 긴 맥락 안에 호출 의도가 섞인 요청
- 혼동하기 쉽지만 호출하면 안 되는 사례
- 선택이 모호한 인접 Skill 쌍
- 선택 없음

이 사례를 먼저 작성하면 description이 실제 업무 경계를 표현하는지 확인하기 쉽다.

## 7.10 좋은 description의 완료 기준

좋은 description은 멋지게 읽히는 문장이 아니다.

같은 평가 요청 모음을 반복했을 때 필요한 Skill을 안정적으로 고르고, 인접 요청에서는 빠지고, 선택 없음 상황에서 억지로 선택되지 않을 때 좋은 description이다.

결국 description 품질은 문장 평가가 아니라 **라우팅 결과**로 판단해야 한다.

# 1장. 프롬프트에서 저장소 지침으로

일회성 프롬프트와 저장소 지침은 비슷해 보이지만 수명이 다르다.

프롬프트는 한 작업을 위해 존재한다. 저장소 지침은 수십, 수백 번의 작업에 반복해서 개입한다. 한 번 잘못 작성된 문장은 한 번의 답변을 망치는 데서 끝나지 않는다. 이후 모든 세션에 같은 편향을 넣을 수 있다.

이 차이 때문에 저장소 지침은 별도의 엔지니어링 대상이 된다.

## 1.1 Persistent instruction의 등장

대표적인 지침 파일은 Claude Code의 CLAUDE.md와 Rules, Codex와 여러 도구의 AGENTS.md, Cursor Rules, Gemini CLI의 GEMINI.md, GitHub Copilot의 custom instructions, Agent Skills 계열의 SKILL.md다.

제품마다 이름은 다르지만 질문은 비슷하다.

> 이 저장소에서 모델이 계속 알아야 하는 것은 무엇인가.

문제는 이 질문을 너무 넓게 해석할 때 시작한다. 계속 알아야 하는 정보와 가끔 필요한 정보, 특정 경로에서만 필요한 정보, 특정 업무를 할 때만 필요한 절차가 한 파일에 섞인다.

## 1.2 지침 파일의 네 가지 역할

실무에서는 지침을 네 종류로 나누면 판단이 쉬워진다.

### 상시 컨텍스트

거의 모든 작업에서 필요한 정보다. 저장소의 핵심 구조, 공통 빌드와 테스트 진입점, 프로젝트 전체에서 항상 지켜야 하는 조건(불변식), 고정된 용어가 여기에 속한다.

### 경로별 규칙

특정 파일이나 디렉터리에서만 필요한 규칙이다. 백엔드 전용 테스트 규칙이나 데이터베이스를 변경하거나 이전하는 마이그레이션(migration) 디렉터리 정책이 대표적이다.

### 업무 절차

특정 요청에서만 필요한 반복 작업 절차(workflow)다. 이런 절차를 한데 묶어 필요할 때 불러오는 기능이 Skill이다. 릴리스 준비, DB 마이그레이션 리뷰, 장애 원인 조사, 보안 점검 같은 절차는 Skill에 더 잘 맞는다.

### 결정론적 강제

모델에게 부탁할 문제가 아니라 시스템이 판정할 문제다. 생성 파일 수정 금지, 금지 명령 차단, 문서 앞부분의 설정 영역(frontmatter) 필수 필드, 코드 서식 정리 도구, 링크 검사 같은 항목은 Hook, 코드 검사, 데이터 구조 규칙(schema), 타입, CI가 더 적합하다.

## 1.3 자연어 파일이 소프트웨어 동작을 바꾼다

지침 파일은 어떤 파일을 읽는지, 어떤 Skill을 선택하는지, 어떤 명령을 실행하는지, 언제 사용자에게 질문하는지, 무엇을 완료로 간주하는지를 바꾼다.

따라서 리뷰의 핵심 질문은 “문장이 잘 쓰였는가”가 아니다.

> 이 문장이 실제 의사결정을 바꾸는가.

삭제해도 모델 행동이 달라지지 않는 문장은 상시 컨텍스트에 둘 이유가 약하다.

## 1.4 저장소 지침의 설계 원칙

좋은 지침은 어떤 내용을 책임지는지 분명하며, 같은 규칙을 여러 파일에 복제하지 않는다. 값을 정확히 확인할 수 있는 기준 원본(canonical source)을 존중한다. 버전, 설정값, 스키마처럼 코드나 설정에서 정확히 읽을 수 있는 값을 Markdown에 복제하지 않는다.

적용 범위가 최소다. 모든 작업에 필요한 것이 아니면 전역 파일에서 빠진다.

검증 가능하다. Skill이라면 호출 조건(trigger)과 실행 결과를 테스트할 수 있고, Hook이라면 허용과 차단 사례를 시험할 수 있다.

그리고 삭제할 수 있다. 과거 모델의 약점을 보완하기 위해 만든 규칙이 영구 정책으로 굳지 않는다.

## 1.5 첫 번째 의사결정 트리

새로운 지침을 추가하기 전에 다음 순서로 판단한다.

1. 모든 작업에 필요한가.
2. 특정 경로에서만 필요한가.
3. 특정 작업에서만 필요한가.
4. 기계적으로 판정할 수 있는가.
5. 이미 더 정확한 자료가 있는가.

이 다섯 질문만으로도 대부분의 루트 지침 비대화를 막을 수 있다.

지침 파일 엔지니어링은 문장을 잘 쓰는 기술보다 먼저, **지식을 어디에 둘지 결정하는 기술**이다.

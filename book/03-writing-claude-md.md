# 3장. CLAUDE.md를 올바르게 쓰기

CLAUDE.md는 Claude Code에서 가장 눈에 띄는 지침 파일이다. 그래서 프로젝트 지식을 모두 넣고 싶은 유혹이 강하다.

하지만 좋은 CLAUDE.md의 목적은 프로젝트 전체를 설명하는 것이 아니다.

> 대부분의 작업에서 항상 필요한 정보만 제공하는 것이 목적이다.

## 3.1 무엇을 넣을 것인가

좋은 후보는 저장소의 한두 문단 설명, 주요 디렉터리와 책임, 공통 build/test/lint 진입점, 프로젝트 전체 불변식, 모델이 반복해서 오해하는 비자명한 사실, 세부 Rule과 Skill로 가는 짧은 포인터다.

Java 백엔드 저장소라면 “Spring을 사용한다” 같은 자명한 설명보다 실제 모듈 구조와 검증 entrypoint가 더 가치 있다.

## 3.2 무엇을 빼야 하는가

특정 기능 체크리스트, 특정 디렉터리 전용 코딩 규칙, 릴리스 전체 절차, migration 전체 매뉴얼, 수백 줄 아키텍처 설명, 스타일 가이드 전문, CLI 옵션 표, 현재 config에서 바로 읽을 수 있는 값은 root CLAUDE.md에서 빠질 가능성이 높다.

이 내용들은 없어지는 것이 아니라 더 적합한 위치로 이동한다.

## 3.3 실제 경로와 진입점을 쓴다

약한 지침은 “변경 후 적절한 테스트를 수행한다”처럼 추상적이다.

더 좋은 지침은 어떤 종류의 변경에서 어떤 검증 경로를 첫 진입점으로 삼는지 알려준다. 다만 세부 옵션 전체를 복제하지 않고 저장소의 실제 script나 build configuration을 source of truth로 둔다.

## 3.4 Nested CLAUDE.md

하위 디렉터리에만 필요한 내용은 더 가까운 scope로 내릴 수 있다.

root에는 저장소 공통 원칙을 두고 backend, frontend, docs에는 각 영역의 규칙을 둔다. 이렇게 하면 frontend 작업에서 backend 전용 규칙이 개입할 가능성이 줄어든다.

제품의 정확한 탐색과 precedence는 버전에 따라 달라질 수 있으므로 사용 시점의 공식 문서를 확인한다.

## 3.5 충돌을 더 강한 문장으로 해결하지 않는다

user-level과 project-level 지침이 충돌할 때 “절대”라는 표현을 추가한다고 확실한 override가 생기는 것은 아니다.

충돌이 자주 발생한다면 scope가 잘못됐는지, 같은 규칙이 복제됐는지, 더 좁은 Rule로 옮겨야 하는지, 기계적 강제로 바꿔야 하는지 검토해야 한다.

## 3.6 200줄 목표의 의미

짧게 유지하라는 조언은 숫자 자체가 목적이 아니다.

루트 파일이 계속 커지는 것은 보통 subsystem 세부사항이 전역으로 올라왔거나, procedure가 상시 컨텍스트에 들어왔거나, 다른 문서를 복제했거나, lint나 Hook으로 옮길 규칙이 prose에 남았다는 신호다.

따라서 줄 수는 품질 점수가 아니라 구조를 다시 볼 신호다.

## 3.7 작성 시 다섯 질문

좋은 root 파일은 대체로 다음 질문에 답하면 충분하다.

1. 이 저장소는 무엇인가.
2. 가장 중요한 디렉터리는 어디인가.
3. 공통 build/test/lint entrypoint는 무엇인가.
4. 모든 변경에 적용되는 불변식은 무엇인가.
5. 세부 규칙과 절차는 어디에서 찾는가.

그 이상이 필요하다면 새 섹션을 추가하기보다 더 좁은 scope가 존재하는지 먼저 확인한다.

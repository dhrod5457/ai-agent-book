# 16장. A/B와 Blinded Eval

지침 A와 B를 비교할 때 어느 쪽이 새 버전인지 알고 평가하면 쉽게 편향된다. “이번에 description을 개선했다”는 사실을 알면 작은 차이도 개선처럼 보일 수 있다. 그래서 지침 평가에서도 어느 버전인지 숨기는 블라인드 비교(blinded comparison)가 유용하다.

## 16.1 기본 비교 단위

가장 단순한 비교는 다음이다.

- 비교 기준: Skill 없음
- 현재: 현재 지침
- 변경안: 변경 지침

필요하면 길이 영향을 구분하기 위한 대조군이나 다른 모델을 추가한다.

중요한 것은 같은 작업과 같은 저장소 상태에서 비교하는 것이다.

## 16.2 Organic prompt

평가 대상에게 “이것은 Skill 평가입니다”라고 알려주면 실제 사용과 다른 행동을 할 수 있다.

가능하면 실제 사용자 요청처럼 요청문을 작성한다.

호출 조건(trigger) 평가에서도 Skill 이름을 직접 넣은 요청문만 사용하면 자연어 Skill 찾기 능력을 평가할 수 없다.

## 16.3 Judge blind

결과를 평가하는 평가자에게 어느 것이 현재 버전이고 변경안인지 숨긴다.

A, B 같은 임의 표시 이름을 사용하고 모델의 식별 정보도 필요하면 숨긴다.

이렇게 하면 “새 버전이 더 좋아야 한다”는 기대를 줄일 수 있다.

## 16.4 Candidate blind

평가 대상에게 평가 기준표(rubric) 전체를 보여주는 것도 조심한다.

평가 기준표를 알고 있으면 실제 업무보다 채점 도구를 만족시키는 행동을 할 수 있다.

실행자는 일반 사용자 요청만 받고, 평가는 별도 단계에서 수행하는 편이 더 현실적이다.

## 16.5 Root monolith vs scoped instruction

A/B 평가는 description뿐 아니라 지침 배치에도 사용할 수 있다.

예:

- B0: 모든 규칙을 최상위 디렉터리 AGENTS.md에 둔다.
- B1: 최상위 디렉터리와 하위 디렉터리의 AGENTS.md
- B2: 최상위 디렉터리 + 경로별 Rules
- B3: 최상위 디렉터리 + 경로별 Rule + 필요할 때 불러오는 Skill

측정할 수 있는 항목:

- 필요한 규칙 준수율
- 관련 없는 규칙의 노출
- 적절한 검증 선택
- 과도한 검증
- 노출 지침 토큰
- 추가 자료 탐색 횟수
- 완료 비용

이 실험은 “하위 디렉터리로 나누면 항상 더 좋다”를 증명하기 위한 것이 아니다. 저장소 규모와 실행 도구에 따라 각 방식에서 얻고 포기할 점(trade-off)이 다를 수 있다.

## 16.6 Instruction Debt A/B

오래된 모델의 부족한 부분을 보완하는 보조 지침(scaffolding)을 제거할 때도 같은 방법을 쓴다.

- C0: 기존 구버전 지침
- C1: 일반론의 반복과 오래된 임시 우회책을 제거한 축소안
- C2: 축소안 + 기계가 검사할 수 있는 규칙을 구조로 이동

측정:

- 작업 성공
- 규칙 위반
- 불필요한 도구 호출
- 과도한 검증
- 토큰
- 응답 지연 시간
- 반복 자기 점검
- 추가 질문 횟수

삭제 후 품질이 유지되면서 비용이 줄면 유지보수 부담 제거의 근거가 된다.

## 16.7 Eval isolation

A/B가 정확하려면 평가 대상 외 조건이 최대한 같아야 한다.

- 같은 시험 환경
- 같은 요청문
- 같은 실행 도구
- 같은 모델
- 같은 Skill 목록
- 같은 저장소 상태
- 새 세션
- 설치된 중복 항목 없음

특히 평가 대상 Skill과 기존 설치된 Skill이 동시에 보이면 Skill 선택(routing) 결과가 오염될 수 있다.

## 16.8 Evaluator permission

평가 도구도 필요 이상으로 강한 권한을 갖지 않는다.

호출 조건 평가인데 전체 파일 시스템 쓰기나 설정 변경 권한이 필요하지 않을 수 있다.

평가 과정의 외부 상태 변화(side effect)가 결과를 바꾸면 실험이 아니라 운영 변경이 된다.

## 16.9 Judge와 사람의 불일치

LLM 평가자 결과와 사람이 실제 산출물(artifact)을 읽은 판단이 크게 다를 수 있다.

이때 즉시 사람 또는 평가자가 틀렸다고 결론 내리지 않는다.

먼저 본다.

- 평가 기준표가 모호한가.
- 길이가 긴 답을 과대평가하는가.
- 정답 표시 이름이 노출됐는가.
- 실제 결과보다 문체를 평가했는가.
- 기계적으로 판정할 수 있는 검증 근거가 누락됐는가.

평가도 디버깅 대상이다.

## 16.10 결과 해석의 절제

A2가 A1보다 좋았다고 해서 “호출하지 않아야 하는 경계는 항상 좋다”고 일반화하면 안 된다.

최소한 다음 맥락을 기록한다.

- 모델
- 실행 도구
- 버전
- 날짜
- Skill 목록
- 작업 평가 자료 모음
- 미리 정한 저장소 시험 환경

이 책이 권장하는 것은 특정 변경안의 승리가 아니다.

> 지침 변경도 다른 소프트웨어 변경처럼 **비교 가능한 조건에서 검증하고 회귀를 남기는 습관**이다.

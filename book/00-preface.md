# 서문

AI 코딩 도구를 오래 쓰다 보면 저장소에 지침 파일이 쌓이기 시작한다.

처음에는 간단하다. 테스트 명령을 적고, 특정 디렉터리를 직접 수정하지 말라고 적고, 배포 전에 검증하라고 적는다. 한두 줄일 때는 문제가 없다. 그러나 프로젝트가 커지고 실패 사례를 하나씩 보완하다 보면 CLAUDE.md, AGENTS.md, Rules, Skills, Hooks가 빠르게 늘어난다. 어느 순간부터는 지침이 모델을 돕는지, 오히려 방해하는지 판단하기 어려워진다.

이 책은 그 지점에서 시작한다.

## 지침 파일은 문서가 아니다

형식만 보면 Markdown이다. 하지만 동작은 문서보다 코드에 가깝다.

지침 한 줄 때문에 모델이 파일을 더 읽고, 다른 Skill을 선택하고, 테스트를 추가로 실행하고, 특정 명령을 피할 수 있다. 잘못된 지침 한 줄 때문에 필요한 Skill이 호출되지 않거나 관련 없는 작업에서 과도한 절차가 실행될 수도 있다.

따라서 지침 파일에는 범위 설계, 책임 분리, 단일 출처, 검증, 회귀 테스트, 버전 관리, 삭제 기준이 필요하다. 이것은 단순한 프롬프트 작성과 다르다.

## 왜 지금 이 주제가 중요한가

2026년의 코딩 에이전트 환경은 빠르게 변하고 있다. 모델은 더 강해졌고, 여러 도구가 AGENTS.md, path rule, Agent Skills 같은 비슷한 개념을 지원하기 시작했다. 동시에 공개 Skill 생태계가 커지면서 새로운 문제가 드러났다.

Skill이 많아질수록 description끼리 경쟁한다. 오래된 가이드는 최신 모델을 과도하게 구속한다. CLI 옵션을 Markdown에 복제하면 실제 도구와 설명이 어긋난다. 배포나 승인처럼 side effect가 큰 업무는 자연어 경고만으로 충분하지 않다.

좋은 지침 시스템은 계속 커지는 시스템이 아니다. 필요 없는 지침을 지우고, 중복을 합치고, 값은 원본에서 읽고, 기계적으로 판정 가능한 규칙은 구조로 옮긴다.

## 이 책에서 하지 않는 것

이 책은 범용 에이전트 프레임워크를 설계하지 않는다. 멀티 에이전트 조직, MCP 서버 구현, LLM API 기반 자동화 시스템도 중심 주제가 아니다.

오직 다음 질문에 집중한다.

> 사람이 저장소에 남기는 지침을 어떻게 설계해야 모델이 필요한 순간에 필요한 정보만 얻고, 잘못된 순간에는 개입하지 않게 할 수 있는가.

## 독자가 얻어야 하는 것

책을 다 읽고 나면 새로운 규칙을 발견했을 때 바로 CLAUDE.md에 추가하지 않게 되는 것이 목표다.

대신 먼저 묻게 된다.

1. 모든 작업에 필요한가.
2. 특정 경로에서만 필요한가.
3. 특정 절차에서만 필요한가.
4. 기계적으로 참과 거짓을 판정할 수 있는가.
5. 더 정확한 canonical source가 이미 있는가.
6. 실제 행동 변화로 검증할 수 있는가.

이 질문들이 지침 파일 엔지니어링의 시작이다.

# 5장. Path-scoped Rules

전역 지침을 줄이는 가장 직접적인 방법은 규칙을 실제 적용 경로로 내리는 것이다.

백엔드 규칙은 백엔드에서만, 문서 규칙은 문서에서만, 배포 규칙은 배포 파일에서만 보이게 한다.

## 5.1 왜 path scope가 필요한가

여러 프로젝트를 한 저장소에서 관리하는 모노레포(monorepo)에는 Java 백엔드, TypeScript 프런트엔드, 기반 시설, 문서, 모바일이 함께 있을 수 있다. 각 영역의 테스트 도구와 규칙이 다르다.

이 모든 내용을 루트 지침에 넣으면 어떤 작업에서도 모든 규칙이 노출된다. 모델은 관련 없는 규칙을 무시해야 하고 때로는 잘못 적용한다.

규칙이 적용되는 경로를 정하면 불필요한 선택지를 줄일 수 있다.

## 5.2 제품별 문법보다 먼저 책임을 정한다

Claude, Cursor, Copilot, 하위 디렉터리의 AGENTS.md는 서로 다른 문법으로 적용 범위를 표현한다. 하지만 먼저 정해야 할 것은 책임이다.

좋은 경로별 규칙은 다음 질문에 답할 수 있어야 한다.

> 이 규칙이 이 경로 밖에서는 왜 필요하지 않은가.

답이 없다면 경로별 규칙이 아니라 전역 규칙일 수 있다.

## 5.3 하나의 Rule에는 하나의 주제

Rule 파일을 작게 나누면 적용 이유가 명확해지고 대상 선택 조건을 좁힐 수 있으며 변경 영향 범위가 줄어든다.

“백엔드 규칙” 하나에 DB, API, 테스트, 문서 규칙을 모두 넣기보다 실제 적용 범위가 다르면 더 나눈다.

## 5.4 Style guide를 Rule로 복제하지 않는다

코드 서식 정리 도구나 코드 검사 도구가 이미 판정하는 스타일을 자연어 Rule로 다시 적는 것은 중복이다.

Rule이 적합한 것은 기계가 바로 알기 어려운 해당 영역의 불변 조건이다. 예를 들어 특정 패키지는 외부 API 타입을 직접 노출하지 않는다거나, 데이터베이스 변경·이전을 위한 마이그레이션(migration) 파일은 이미 작성된 경우 수정하지 않는다거나, 자동 생성된 디렉터리는 생성 도구를 통해서만 바꾼다는 정책이 여기에 속한다.

## 5.5 Scope drift

경로별 규칙도 시간이 지나면 낡는다. 디렉터리가 이동하고 확장자가 바뀌고 모노레포 구조가 재편되면 대상 선택 조건이 아무 파일에도 맞지 않을 수 있다.

따라서 구조 검사 도구(structural validator)가 대상 선택 조건 문법, 조건에 맞는 파일이 실제로 있는지, 하위 디렉터리 지침 위치를 검사할 가치가 있다.

## 5.6 Parent와 child의 관계

좋은 구조는 같은 정책을 상위 지침과 하위 지침에 복제하지 않는다.

최상위 디렉터리에는 “가장 좁은 충분한 검증부터 수행한다”는 공통 원칙을 두고, 백엔드에는 해당 모듈 테스트, 프런트엔드에는 해당 패키지 테스트·코드 검사처럼 각 영역에 맞는 구체적인 규칙을 둔다.

## 5.7 완료 기준

경로별 설계가 잘 되었는지는 관련 없는 작업에서 해당 영역의 규칙이 노출되지 않는지, 필요한 경로에서 규칙이 빠지지 않는지, 상위 지침과 하위 지침이 모순되지 않는지, 코드 서식 정리 도구가 잡는 내용이 중복되지 않는지로 확인한다.

경로 적용 범위의 목적은 파일을 나누는 것이 아니다.

> **작업에 필요한 지침만 작업 가까이에 두는 것**이 목적이다.

# 부록 A. 실전 체크리스트

이 체크리스트는 점수를 만들기 위한 것이 아니다. 목적은 파일 유형별로 실제 실패 유형에 필요한 계약이 빠졌는지 빠르게 확인하는 것이다.

## A.1 모든 instruction file 공통

### Ownership

- 이 파일이 소유하는 지식의 종류를 한 문장으로 설명할 수 있는가.
- 다른 지침 파일과 같은 규칙을 중복 소유하지 않는가.
- 더 정확한 기계가 읽을 수 있는 자료가 있으면 값을 복제하지 않았는가.

### Scope

- 저장소 전체 규칙만 루트의 상시 지침에 있는가.
- 특정 경로에만 필요한 규칙은 하위 디렉터리 지침 또는 경로 Rule로 내려갔는가.
- 특정 작업의 절차는 Skill로 분리했는가.
- 기계적으로 검사 가능한 규칙은 검사 도구, 코드 검사, Hook, CI로 이동할 수 있는가.

### Freshness

- 바뀔 수 있는 버전, API, 상태 정보를 고정된 설명문에 무기한 박아 두지 않았는가.
- 기준 원본(canonical source)이 명확한가.
- 대체 자료로 보존한 사본에는 출처와 날짜가 있는가.
- 현재 상태 확인 실패 시 추측하지 않는가.

### Maintenance

- 저장소 내부 참고 자료가 실제 존재하는가.
- 삭제 조건을 설명할 수 있는가.
- 모델 또는 실행 도구 업그레이드 시 삭제 후보를 다시 보는가.

## A.2 CLAUDE.md / AGENTS.md

- 모든 작업에 필요한 정보만 상시 문맥 정보에 있는가.
- 하위 시스템 세부사항이 최상위 디렉터리에 쌓이지 않았는가.
- 일반 개발 안내서를 그대로 복사하지 않았는가.
- 빌드·테스트 시작점이 실제 저장소와 일치하는가.
- 작업 절차 전체가 최상위 디렉터리에 들어 있지 않은가.
- 하위 디렉터리 지침, Rule, Skill로 가는 참조 링크가 있는가.
- 실행 도구에만 적용되는 규칙을 여러 도구에서 통하는 규칙처럼 쓰지 않았는가.

### 리팩터링 신호

- 최상위 디렉터리 파일이 계속 커진다.
- “항상 먼저 읽어라” 문서가 늘어난다.
- 같은 테스트와 스타일 규칙이 여러 곳에 반복된다.
- 현재 모델이 이미 잘하는 일반론이 많다.
- 릴리스, 배포, 데이터베이스를 변경하거나 이전하는 마이그레이션(migration) 절차가 최상위 디렉터리에 들어 있다.

## A.3 Path-scoped Rule

- 대상 선택 조건이 실제 필요한 파일만 잡는가.
- 이 규칙이 해당 경로 밖에서는 필요하지 않은가.
- 상위 지침과 같은 정책을 장문으로 복제하지 않았는가.
- 서식 정리 도구와 코드 검사 도구가 판정하는 내용을 중복하지 않았는가.
- 경로가 이동하면 대상 선택 조건도 검토되는가.
- 현재 저장소에서 대상 선택 조건이 실제 파일과 매치되는가.

## A.4 Auto-trigger SKILL.md

### Trigger

- description에 무엇을 하는지가 있는가.
- 언제 사용하는지가 있는가.
- 혼동하기 쉽지만 호출하면 안 되는 사례가 필요한가.
- 분야 전체를 무조건 잡지 않는가.
- 선택 없음 또는 선택 보류가 가능한가.

### Preconditions

- 필요한 파일, 상태, 도구, 설정이 명시됐는가.
- 없는 값을 임의로 만들지 않는가.
- 사전 조건 실패 시 대체 경로 또는 중단이 있는가.

### Procedure

- 순서가 실제 결과에 영향을 주는 단계만 강하게 고정했는가.
- 판단이 필요한 단계와 기계적으로 정해진 단계를 구분했는가.
- 긴 매뉴얼과 목록을 복제하지 않았는가.
- 참고 자료를 조건부로 읽는가.

### Evidence

- 완료를 모델 자신의 선언으로 판정하지 않는가.
- 테스트, 출력, 산출물(artifact), 실행 기록, 상태 같은 증거가 있는가.
- 범위가 좁은 Skill에는 명확한 Done when을 둘 수 있는가.

### Handoff

- 어디서 멈추는가.
- 다음 Skill, 도구, 사람에게 넘기는 조건이 있는가.
- 더 이상 권장하지 않는 시작점이 전체 처리 로직을 복제하지 않는가.

### Eval

- 호출 의도가 명확한 사례가 있는가.
- 이름을 말하지 않아도 호출해야 하는 사례가 있는가.
- 혼동하기 쉽지만 호출하면 안 되는 사례가 있는가.
- 혼동하기 쉬운 Skill 쌍이 필요한가.
- 평가 대상과 설치된 Skill이 충돌하지 않는 환경에서 평가하는가.

## A.5 Manual-only Skill

- 사람이 이름과 호출 방법을 찾을 수 있는가.
- 입력 인자의 규약이 명확한가.
- 자동 호출 평가에서 제외되는가.
- 명시적 호출이 필요한 이유가 있는가.
- 실패와 재시도 동작이 있는가.
- 외부 상태 변화(side effect)가 크면 승인과 검증 근거가 있는가.

## A.6 High-side-effect Skill

### Intent

- prepare/preview와 execute/publish를 구분하는가.
- 사용자 요청이 실제 상태 변경 의도를 포함하는가.
- 일상적으로 수행하며 되돌릴 수 있는 단계에 불필요한 승인을 요구하지 않는가.

### Authority

- 상태 변경 책임자(state owner)가 명확한가.
- 이 Skill이 바꾸면 안 되는 상태가 있는가.
- 검증 권한과 실행 권한을 분리해야 하는가.

### Permission

- 필요한 도구 권한만 사용하는가.
- 비밀 정보를 저장소 파일에 남기지 않는가.
- 같은 효과를 내는 우회 경로를 검토했는가.

### Failure

- 실패가 성공 상태로 남지 않는가.
- 실행이 중단된 뒤 정리 절차가 있는가.
- 비용과 자원 누수 가능성을 다뤘는가.

### Evidence

- 상태 변경 결과를 확인할 식별자나 상태가 있는가.
- 완료 선언이 실제 실행 결과와 연결되는가.

## A.7 Validation / Test Skill

- 테스트가 실제로 읽기 전용인가.
- 외부 기반 시설이나 비용을 사용할 수 있는가.
- 가장 좁은 충분한 테스트부터 실행하는가.
- 변경 범위에 집중한 테스트와 전체 회귀 테스트를 구분하는가.
- 시간 제한이 필요한가.
- 불안정한 테스트나 캐시 때문에 잘못 통과하는 경우(false positive)를 구분하는가.
- 의심스러울 만큼 쉽게 통과한 테스트가 실제 실패도 감지하는지 확인할 수 있는가.

## A.8 Fast-moving framework / CLI / API Skill

- 현재 판단의 기준이 되는 원본이 무엇인가.
- 설치된 버전과 최신 버전을 구분하는가.
- 기존 프로젝트와 새 프로젝트의 기준을 구분하는가.
- CLI 옵션 표를 고정된 Skill 문서에 복제하지 않았는가.
- help, 자동 생성된 데이터 구조 규칙(schema), 설치된 문서, 현재 확인할 수 있는 문서 중 올바른 자료를 쓰는가.
- 현재 자료 확인에 실패했을 때 대체 경로가 있는가.
- 사용자가 지정한 대상을 무시하고 최신 버전을 강제하지 않는가.

## A.9 Hook

- Hook이 필요한 실제 실패 유형이 있는가.
- 대상 선택 조건이 위험 적용 영역만 잡는가.
- 차단되어야 하는 사례의 테스트가 있는가.
- 위험한 작업과 비슷해 보여도 정상 작업을 허용하는지 확인하는 테스트가 있는가.
- 도구 인자의 실제 의미를 정확히 모델링하는가.
- 같은 효과를 내는 우회 방법을 검토했는가.
- 외부 상태를 바꾸는 작업을 여러 번 실행해도 한 번 실행한 것과 결과가 같은가(idempotent).
- 작업 공간의 신뢰 여부를 고려했는가.

## A.10 최종 열 질문

1. 언제 활성화되는가.
2. 언제 활성화되면 안 되는가.
3. 시작 전에 무엇이 참이어야 하는가.
4. 상태와 권한 관리 책임자는 누구인가.
5. 어떤 절차가 실제로 필요한가.
6. 어떤 외부 상태 변화와 권한이 있는가.
7. 무엇으로 완료를 증명하는가.
8. 어디서 멈추고 인계하는가.
9. 바뀌는 사실은 어디서 다시 읽는가.
10. 어떤 실패나 평가가 이 지침을 수정하거나 삭제하게 하는가.

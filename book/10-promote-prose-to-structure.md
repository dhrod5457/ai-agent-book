# 10장. Hook, lint, CI, type으로 승격하기

지침 파일이 계속 커지는 가장 큰 이유 중 하나는 반복 실패를 모두 자연어 규칙으로 고치려 하기 때문이다.

“이 파일은 수정하지 마라.”
“이 명령은 실행하지 마라.”
“변경 후 코드 서식 정리 도구를 실행하라.”
“문서 앞부분의 설정 영역(frontmatter)에는 이 필드가 있어야 한다.”

이런 규칙을 계속 CLAUDE.md나 Skill에 추가하면 모델은 매번 읽고 기억하고 판단해야 한다.

하지만 일부 규칙은 판단이 필요 없다.

## 10.1 지침과 enforcement의 차이

자연어 지침은 행동을 유도한다. 반면 코드 검사(lint), 타입(type), 데이터 구조 규칙(schema), 지속적 통합 검사(CI), 특정 사건에 연결된 자동 실행 절차(Hook)는 기계적으로 허용 여부를 판정한다.

따라서 먼저 묻는다.

> 이 규칙의 위반을 기계가 명확하게 판정할 수 있는가.

그렇다면 자연어 설명만으로 둘 이유가 약하다.

## 10.2 구조적 승격 사다리

반복되는 수정 요청이 있으면 다음 순서로 더 강한 표현 수단을 검토한다.

1. 코드 구조나 타입으로 불가능하게 만들 수 있는가.
2. 데이터 구조 규칙이나 검사 도구로 판정할 수 있는가.
3. 코드 검사나 CI로 검사할 수 있는가.
4. Hook으로 작업 생명주기에 연결할 수 있는가.
5. 공통으로 사용하는 기준 도우미나 스크립트로 한 경로만 제공할 수 있는가.
6. 그래도 판단이 필요하면 Rule, Skill, CLAUDE.md에 남긴다.

이 순서는 강한 장치가 항상 더 좋다는 뜻이 아니다. 가장 자연스러운 판단의 기준이 되는 원본을 먼저 찾는다는 뜻이다.

## 10.3 Type과 schema

가능하면 잘못된 상태를 표현하기 어렵게 만든다.

예를 들어 메타데이터(metadata) 필수 필드는 자연어 설명으로 “반드시 넣어라”라고 적는 것보다 데이터 구조 규칙 검증이 더 강하다.

상태 전이를 기계가 읽을 수 있는 형식으로 표현하면 단독 변경 책임자 충돌도 검사 도구가 잡을 수 있다.

## 10.4 Lint와 CI

정적 파일 내용이나 저장소 안의 파일과 구성 요소 사이의 연결 관계를 검사할 수 있다면 코드 검사와 CI가 적합하다.

- 끊어진 저장소 내부 참조
- 중복 항목 등록
- 잘못 작성된 문서 앞부분의 설정 영역
- 구성 목록(manifest) 누락
- 직접 수정이 금지된 생성 파일을 수정한 경우
- 존재하지 않는 스크립트 경로

이런 오류를 LLM 평가자로 판정할 필요가 없다.

## 10.5 Hook

Hook은 특정 작업 생명주기의 사건에서 검사를 실행하거나 작업을 막아야 할 때 유용하다.

예:

- Bash 명령 실행 전 위험한 패턴 검사
- 파일 수정 후 코드 서식 정리 도구 실행
- 특정 파일 변경 후 검사 도구 실행
- publish 계열 상태 변경 전에 승인 상태 검사

Hook은 지침보다 결정론적이지만 실행 권한과 외부 상태 변화(side effect)를 가지므로 더 높은 보안 기준이 필요하다.

## 10.6 모든 것을 Hook으로 만들지 않는다

아키텍처 선택, 읽기 쉬움, 작은 변경 선호, 호환성을 위해 얻고 포기해야 하는 점(trade-off)처럼 맥락과 판단이 필요한 기준은 Hook에 적합하지 않다.

기계적으로 명확하지 않은 품질을 정규식이나 작업을 차단하는 Hook으로 만들면 정상 작업을 잘못 차단하는 오탐(false positive)이 늘어난다.

구조적 강제의 목적은 자연어를 없애는 것이 아니다.

> 사람이 판단할 필요가 없는 문제를 자연어 추론에서 빼는 것.

## 10.7 Prose-only safety gate의 한계

“절대 승인 없이 publish하지 마라”라는 Skill 문장만으로는 우회 경로를 모두 막기 어렵다.

다른 Skill이나 직접 도구 호출이 같은 상태 변경을 실행할 수 있다.

외부 상태 변화가 큰 작업은 필요에 따라 다음을 조합한다.

- 사용자의 실행 의도를 확인하는 규칙
- 권한 정책
- Hook
- 차단되어야 하는 사례의 테스트
- 위험한 작업과 비슷해 보여도 정상 작업은 허용되는지 확인하는 테스트

중요한 것은 모든 것을 막는 것이 아니라 실제 위험 경계를 정확히 모델링하는 것이다.

## 10.8 Structural validator의 경계

좋은 검사 도구는 의미를 평가하지 않는다.

잘하는 질문:

- 파일이 존재하는가.
- YAML이 구문 분석되는가.
- 필수 필드가 있는가.
- 참고 자료가 존재하는가.
- 대상 선택 조건이 유효한가.
- 중복 항목 등록이 있는가.

하지 말아야 할 질문:

- description이 좋은가.
- 작업 절차(workflow)가 합리적인가.
- 500줄을 넘었으니 나쁜가.
- MUST가 많으니 나쁜가.

이런 항목은 의미와 행동 평가나 사람의 검토로 보내야 한다.

## 10.9 승격 후 prose도 줄인다

기계적 강제를 추가하고도 기존 자연어 규칙을 그대로 남기면 중복이 생긴다.

예를 들어 검사 도구가 문서 앞부분의 설정 영역 데이터 구조 규칙을 완전히 검사한다면 CLAUDE.md에 필드 목록을 장문으로 유지할 필요가 없다.

대신 다음처럼 줄일 수 있다.

> Skill 변경 후 저장소 검사 도구를 실행한다.

구조적 승격의 최종 목적은 **규칙을 더 많이 만드는 것**이 아니라 **하나의 기준 원본을 만드는 것**이다.
